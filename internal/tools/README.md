# Refactor tools

Tools that prove a refactor changed nothing it should not have. They belong
to step S14a of the refactor plan (`docs/plans/codebase-refactor.md`), the
window generators to S14c–S14f, and they back its verification classes
(§4.2): class **A** (pure move) is proved by
`declhash` and `tsmovecheck`, generated by `declmove`, and reviewed from the
`movecheck` map; class **B** boot stages (M4) are inlined for review, and
their shape checked, with `movecheck -flatten`; M11a's class B split of the
MCP tool table is generated, and proved, by `splittools` (S14e); F1's class A
split of the frontend's API client is generated by `tsdeclmove` (S14f) and
proved by `tsdeclhash` and `tsmovecheck`. Each Go tool is a stdlib-only `package main`, run with
`go run` from the repository root; none touches `go.mod`. Every tool
exits 2 when a path it is given holds no source on either side (a mistyped
path, a Go `./...` pattern, which none of them expands, or an unexpanded
glob), so a check never passes by comparing nothing; a package or module
present on one side only is a creation or deletion, not an error (except
for `splittools -check`, which needs the table on both sides).

The three S14a Go tools share `decls.go` and `effects.go` byte for byte (the S1 architecture test
freezes the module's import edges, so they cannot import a common package);
`declhash`'s `TestSharedFileIsIdentical` keeps the copies equal. Edit
the files under `declhash/` and copy them over the other two. `splittools`
shares neither: it reads only the one package it splits.

`liftmigrations` (step S14d) is a window generator: it produces refactor
step M10 from the migration registry, so that move is regenerated on the
latest `master`, never rebased (R4). It shares no file with the three tools
above; its own tests prove its output with `declhash`.

## declhash

```
go run ./internal/tools/declhash [-o manifest] [-tests=false] <pkg dir>...
go run ./internal/tools/declhash -compare base.txt head.txt
go run ./internal/tools/declhash -base <git-ref> [-head <git-ref>] <pkg dir>...
```

Hashes every package-level declaration: functions, methods (`(*T).Name`,
`T.Name`), types, vars and consts, one entry per name of a grouped spec (a
const keeps its implicit type and value, and its iota when it uses iota).
The hash covers the go/printer rendering with doc and inner comments, the
file's build constraints, and the import path behind each package
qualifier; file names and import blocks are not part of it, so moving
declarations between files leaves the manifest identical. Two package-wide
entries (`effects.go`, shared like `decls.go`) cover what initialisation
does: `(blank imports)`, the side-effect imports with their files' build
constraints (`_ "embed"` excepted), and `(init order)`, the order the init
functions run in and the order of every package-level var whose
initialiser calls something not known to be pure (S1's pure-constructor
list), with the vars those initialisers read. Dropping a blank import, or a
move that reorders inits or side-effecting initialisers across files,
therefore fails; moving `var errX = errors.New(...)` does not. `-base` compares
a git ref with the working tree (or `-head`) without checking anything out
and exits 1 on any added, removed or changed declaration. Used by every
class-A step, per commit (M1, M5–M9, M10's and M11a's move commits, M12),
and by the S14b guard job.

## declmove

```
go run ./internal/tools/declmove [-n] [-goimports=false] -spec internal/tools/declmove/specs/<step>.json
```

Moves declarations between the files of one package as a committed spec
says, keyed by declhash name (rule R4: a move PR is regenerated on the
latest master, never rebased). Each declaration moves with its doc comment,
in spec order; a new target file gets the spec's header comment and the
package clause. The moved code takes its imports with it, sources drop the
imports only it used, an emptied file is deleted, and the pinned goimports
(`golang.org/x/tools/cmd/goimports@v0.42.0`, one constant in `main.go`)
tidies the touched files. It refuses a missing or ambiguous name (pick a
duplicate with `Name#2`) and a grouped declaration that is not moved whole,
then checks its own result: the package's declhash manifest must be
unchanged, or every file is restored. `-n` prints the moves only.
`specs/example.json` shows the format (the shape of M1's move commit). Used
by M1, M5–M9 and M12; the spec goes in the PR.

## movecheck

```
go run ./internal/tools/movecheck [-tests] [-head <ref>] <pkg dir>
go run ./internal/tools/movecheck [-tests] -base <ref> [-head <ref>] <pkg dir>
go run ./internal/tools/movecheck -flatten <func> [-recv a] [-base <ref>] <pkg dir>
```

Prints the declaration-to-file map (`key -> file.go`), or with `-base` only
what changed file (`key: old.go -> new.go`): the map a move PR's
description carries (§6.5) and a hot-file move's heads-up posts (§6.9).
`-flatten main` prints `main()` with every `a.<stage>()` call inlined from
the `wire_*.go` stage methods, and fails if a stage has a value receiver or
contains `defer`, `recover` or a return before its last statement; with
`-base` it prints a diff of the flattened statements against the ref and
exits 0. That diff is for review: locals renamed to `a.field` show up as
changed lines, so it does not by itself prove that only renames differ.
Normalising those renames and failing on any remaining difference is an
open follow-up for S14c, before M4. Used by M4 (with S14c's
`stageextract`), and by M6–M9 for their maps.

## liftmigrations

```
go run ./internal/tools/liftmigrations -spec internal/tools/declmove/specs/M10.json [-n] [dir]
go run ./internal/tools/liftmigrations [-n] [-build=false] [dir]
```

Generates M10, one file per migration, from `var migrations = []Migration{...}`
in `internal/persistence/postgres` (or `dir`), in two commits. Used by M10,
and after it to move a migration written the old way into its own file:

1. **Class A, the helper and runner move.** `-spec` writes the `declmove`
   spec and changes nothing else: every declaration of the registry's file
   but the registry and its element type (`Migration`, with any methods)
   leaves it, in source order. What a registry entry reaches, directly or
   through other declarations, goes to `migration_helpers.go`
   (`backfillRefPrefix` and `embeddingDimensions` today); the rest, the
   runner, the ledger, the locks and the reconcile, to `migrate_runner.go`.
   Then `go run ./internal/tools/declmove -spec
   internal/tools/declmove/specs/M10.json` moves them, proves the package's
   `declhash` manifest unchanged and tidies imports with the pinned
   goimports. The spec goes in the commit.
2. **Class B, the lift.** Without `-spec`, each entry whose `Run` is a
   function literal becomes `func m00NN<Name>(tx *sql.Tx) error` in
   `migration_00NN_<name>.go` (`unique_personal_org_per_user` becomes
   `m0002UniquePersonalOrgPerUser` in
   `migration_0002_unique_personal_org_per_user.go`), with the comment
   above the entry, and the entry becomes one line naming it. The registry
   stays an explicit, ordered list, with no `init()`. An entry that already
   names a package-level function (the 0001 baseline's `RunDB: InitSchema`,
   or one lifted before) is left as it is, with its comment, so a second
   run changes nothing, and a migration still written as a literal, such as
   one on a branch that merges `master` after M10, is lifted on its own.

The lifted body is the literal's source text, re-indented by gofmt: code
lines move one tab left, and raw strings keep every byte, so the SQL inside
them keeps its old indentation (the S3 freeze hashes literals byte for
byte). The comment above an entry becomes the function's doc comment,
except where gofmt would reword a doc comment: it turns two single quotes,
SQL's empty string, into a typographic quote, so the comments of 0014 and
0017 stay above their functions word for word, separated by a blank line.
The imports only the lifted bodies used leave the registry's file.

Before it stops, the lift re-reads the package and checks that nothing but
the layout changed, restoring every file and exiting 1 if not: the registry
holds the same entries in the same order; each lifted function is its
literal token for token, comments and raw-string bytes included, and its
go/printer text without comments, what the S3 freeze hashes, is the
literal's; the comment above it is the entry's, line for line; each new
file declares its function alone, imports exactly what its body uses, and
has no other comment; the registry's file, outside its imports, is the
original with only the lift's edits, token for token; every comment the
registry's file had is still there, in order, in it or in the lifted file
of the entry it was above or inside (a check that reads the files, not the
lift's plan, so a planning fault that loses or reorders a comment cannot
hide behind it; one that hands a comment to the neighbouring migration in
the same order is not caught); every other
declaration of the package is byte-identical; and `go build` passes
(`-build=false` skips that). It refuses, writing nothing, what it cannot
carry: a `Run` that is neither a literal nor a function's name, a name that
cannot be part of a file name, a name whose file the go command would read
as a test or build for one platform only (one ending in `test` or in an
operating system or architecture: `_test`, `_linux`, `_windows`, `_amd64`,
`_arm`), a function or file that exists, versions out of order, a comment
inside an entry but outside its function, two entries on a line, build
constraints or a dot import in the registry's file. `-n` prints the
function-to-file map (what the heads-up on the tracking issue posts, §6.9)
or the spec, and writes nothing.

After each commit, run `UPDATE_RATCHETS=1 go test ./internal/archtest`
and commit `ratchets.json` with it: the move lowers `migrations.go`'s
ceiling, and the lift, which leaves it about 110 lines, removes it. Nothing
is added: every new file and function fits the K14 budgets.

The tests run on `testdata/fixture`, a registry in each shape the real one
has, against the goldens under `testdata/want`
(`UPDATE_GOLDEN=1 go test ./internal/tools/liftmigrations -count=1 -run '^(TestLiftFixture|TestSpecFixture)$'`
regenerates them when the tool changes on purpose), plant each fault the
self-check must catch, and, without `-short`, run the whole recipe on a copy
of this repository (`TestLiftTheWorkingTree`): `declhash` identical after
the move and different only in the registry and the new functions after the
lift, the module building, `go test ./internal/archtest` passing with
`ratchets.json` as it is, the S3 freeze passing against its goldens, and
with `OPENV_TEST_DATABASE_URL` set the schema and purge goldens and the
migration tests too; `migrations.go` ends at most 150 lines, one line per
entry in its registry. Once M10 has landed the working-tree test skips,
since there is nothing left to lift, even when a later change has put a
declaration beside the registry for `-spec` to move (`TestRecipeAfterM10`
runs that case on the fixture).

## splittools

```
go run ./internal/tools/splittools [-n] [-vet=false] -spec internal/tools/splittools/specs/M11a.json
go run ./internal/tools/splittools -check -base <ref> [-head <ref>] [-func Tools] internal/mcp
```

Generates M11a's class B commit (S14e, rule R4): the entries of the MCP
tool table, the `[]Tool` literal `internal/mcp`'s `Tools()` returns, move
into per-area constructors in new `tools_<area>.go` files, and `Tools()`
returns `slices.Concat` of them in today's order. `specs/M11a.json` names
each constructor, its file, its doc comment and its tools by `Name`, with a
header per file; `-n` prints the tool-to-constructor map (the map the M11a
pull request's description carries) and each constructor's span, and
writes nothing. Each entry moves as the whole lines it occupies, with the
comment lines above it and the comment after it, into a constructor at the
literal's own depth, so the moved lines are the old ones byte for byte
(`git diff --color-moved` shows only moves); each new file imports what its
entries use, named as `tools.go` names it, and `tools.go` drops the imports
only they used and gains `slices`. The spec is keyed by name, so it
survives edits to the entries: a tool it does not name joins the
constructor of the tool before it, a name `Tools()` no longer has is left
out, and a constructor left empty is not written, each with a note; an order
the concatenation could not reproduce, a tool listed twice, a constructor
over K14's 100 lines, a new file over 800, a name the package already
declares, an existing target file, a `_GOOS`/`_GOARCH` or `_test` file name,
and any shape it could not move whole (a comment outside the entries, two
entries on one line, an entry without a `Name` string, a dot import, a
table file with build constraints the new files would not carry) are
refused, and nothing is written. Each of those refusals is the spec's to
settle, and carries `errPlan`, which the tests tell from a fault. Before
writing, it checks its own result: `Tools()` flattened through the
constructors returns the same entries in the same order, each rendered
identically with its comments; every other declaration of the package,
with the import paths its qualifiers resolve to, is unchanged; `Tools()`
keeps its doc comment and signature; and each constructor's span and each
new file's length, measured as `internal/archtest` measures them, is what
it planned and within K14. After writing it runs `go vet` on the package
and restores every file if that fails. On its own output it finds nothing
to split and says so. It exits 0 on success, 1 on a refusal, 2 on a usage,
spec or read error (a package directory with no Go file included).

`-check` is the proof a reviewer of M11a's class B commit runs: it compares
the package at a git ref with the working tree (or `-head`) with the
self-check's comparisons (its size checks are `internal/archtest`'s in
CI), and prints the head side's map. It exits 1 on an entry of `Tools()`
added, dropped, reordered or changed, whichever shape each side has, naming
the tool and the first line that differs; on any other declaration of the
package added, dropped or changed, with the import paths its qualifiers
resolve to, matched by name, so that a declaration M11a's class A commit
moves to another file is no change; and on `Tools()`'s doc comment or
signature changed. It compares declarations, not files: which file holds
one, a blank import and a build constraint are left to
`git diff --color-moved` and the S7 goldens. After generating, M11a runs
`UPDATE_RATCHETS=1 go test -count=1 -run '^TestArchitecture$' ./internal/archtest`,
which drops `internal/mcp/tools.go`'s `file_lines` and `internal/mcp:Tools`'s
`func_lines` entries, and commits the result, as the Refactor guard requires
of a refactor. M11a's class A commit (the client, the serve loop and the
schema helpers into their own files) is `declmove`'s, with a spec of its own.

Its tests: the unit tests split `testdata/fixture` (a table in
`internal/mcp`'s shape, with comments above, inside and after entries, a
named import, a module import, a blank import and a local variable named
like an import), compare every written file, vet and test the result, and
cover each refusal, the spec drift above, `-check` on a git repository and
the exit statuses, and tamper with a rendered split to prove the self-check
refuses each kind of damage. `TestM11aOnD11dee8` runs M11a's spec on
`testdata/d11dee8`, a copy of `internal/mcp`'s production files at
`d11dee8` (compared with git's copy wherever `d11dee8` is reachable; CI's
shallow checkout is not), with a stub for the one module package they
import. `TestM11aOnTheWorkingTree`, skipped under `-short`, generates M11a
on a copy of this module and proves it as M11a's pull request would: `go
vet` of `internal/mcp` and `cmd/openv-mcp`; `go test` of those,
`internal/seeds` (M11's `interviewer_test.go`) and `internal/archtest`;
`UPDATE_RATCHETS=1` removing or lowering entries only; and the S7 goldens
under `internal/mcp/testdata`, rewritten with `UPDATE_GOLDEN=1`, byte for
byte the committed ones. It skips once M11a has merged, when `Tools()` no
longer returns a literal, and on a refusal marked `errPlan`, which it
names: a feature pull request that adds or grows a tool is never failed
for a budget or a shape (§8.4), and M11a's author settles the refusal in
`specs/M11a.json` when regenerating the split (R4). A proof that fails
after the split still fails the test. The spec leaves R6's 10% headroom:
on `d11dee8`'s table no constructor spans more than 90 lines (the largest,
`linkTools`, 82), which `TestM11aOnD11dee8` checks. The independent byte
check forgives only the blank lines above a constructor's first entry,
which splittools drops, and names the constructor and the first line that
differs.

## frontend/scripts/tsdeclhash.mjs

```
node frontend/scripts/tsdeclhash.mjs [--root dir] [--no-module] [-o manifest] [path...]
node frontend/scripts/tsdeclhash.mjs --compare base.txt head.txt
node frontend/scripts/tsdeclhash.mjs --base <ref> [--head <ref>] [--no-module] [path...]
```

The TypeScript counterpart of declhash, over `frontend/src` by default: one
entry per top-level declaration (`module<TAB>name<TAB>sha256`), imports and
export wiring excluded; a side-effect import (`import './x.css'`) is a
declaration, `(import src/x.css)`. A hash covers the text with its attached
comments and what each module-level name it uses is bound to, by content,
so a moved dependency still matches and a rebinding does not. A module
path passed to a call (`vi.mock('../api/client')`, `import('./x')`) is
bound to what each name that module exports resolves to, so splitting a
module behind a barrel that re-exports the same names leaves every
`vi.mock` of it alone. A declaration that must become importable from its
new module is exported with an `export { name }` list, not by adding the
`export` modifier, which changes its text; S14f's `tsdeclmove` follows
that rule for F1's `API_BASE_URL`, `client`, `uploadConfig`, `saveBlob` and
`downloadBlob` (`ARTIFACT_PAGE_LIMIT` moves with `artifactAPI`, its one
user, and needs no export). `--no-module` compares declarations wherever
they live, as F1 needs.

## frontend/scripts/tsmovecheck.mjs

```
node frontend/scripts/tsmovecheck.mjs [--root dir] [--head <ref>] <base-ref> [path...]
```

Fails unless the only differences from the base ref are wiring (imports,
re-exports, export lists) and declarations that moved between modules
unchanged; prints each move. Module evaluation order is part of the proof:
runtime statements that stay together in a module keep their order, a
module's imports keep their relative order as compiled (type-only imports
do not count), no new runtime import cycle appears, and a statement that
may have side effects (a call not known to be pure, `new`, an assignment, a
side-effect import of a script, outside function bodies) moves only as part
of its module's whole set of them, in order, into a new module the old one
loads, which is F1's shape for the axios instance and its interceptors. Any
other move of such a statement is refused rather than certified. When none
of those fails, it also checks what loading each module on both sides runs:
the statements with side effects it reaches, each module once and its
imports first, as ESM evaluates them, must run in the same order (those
that run on one side only are not compared). That catches a split that
changes which module loads an import first: with a module's statements
moved to a new one it loads first, a module with side effects that only
another new module still imports (one that sets axios's defaults, say) now
runs after them ("effects reordered when <module> loads"). The limits: CSS
cascade order across modules is S12b's, and getters are assumed pure. Used
by F1 and any class-A TS move. Both scripts use
`frontend/node_modules/typescript` (run `npm ci` first); their tests run
with `cd frontend && node --test 'scripts/*.test.mjs'`, in CI's frontend
job.

## frontend/scripts/tsdeclmove.mjs

```
node frontend/scripts/tsdeclmove.mjs [--root dir] [-n] [--no-typecheck] --spec frontend/scripts/specs/F1.json
```

Generates F1 (S14f, rule R4): the declarations of `src/api/client.ts` move
into new modules and `client.ts` becomes a barrel with the same exports, so
no import site changes and every whole-module `vi.mock` of it keeps
intercepting. `specs/F1.json` is keyed by declaration name, as tsdeclhash
names them: the axios instance, both interceptors, `uploadConfig`,
`API_BASE_URL`, `saveBlob` and `downloadBlob` go to `api/http.ts`; the 145
types to 13 `api/types/<area>.ts`; the 54 `xxxAPI` objects and the six other
values to 13 `api/<area>.ts` (artifacts, projects, attachments, vv, guided,
agents, account, orgs, billing, runners, community, notifications,
platform). On today's `client.ts` (2,886 lines, 212 declarations) the
barrel is 42 lines and the largest module, `api/types/projects.ts`, 289;
`-n` prints the declaration-to-module map that F1's heads-up posts (§6.9)
and writes nothing.

Each declaration moves as the whole lines it occupies, with every comment
above it and the comment on its last line, in source order; neighbours in
the source that stay neighbours keep the text between them byte for byte,
so `git diff --color-moved` shows moved blocks. A statement that declares
nothing (the interceptors) moves with the runtime declaration before it.
Each module imports what it uses, named as `client.ts` named it: a moved
name from its new module (`import type` when only types or type
declarations use it), an import of `client.ts`'s with its specifier
rewritten. A declaration another module uses that has no `export` modifier
is exported with an export list at the end of its module: `export { ... }`
for values and `export type { ... }` for types, which `isolatedModules`
requires (TS1205), as `import type` imports them. The barrel keeps
`client.ts`'s wiring as it was (its re-export of `baseURL`, and
`export default client;`, now importing `client` from `api/http.ts`) and
re-exports each module: `export type *` from a module of types only, which
the build erases, `export *` from one whose exports are all `client.ts`'s,
a named list from any other. Its surface is S12's snapshot, unchanged.

The spec survives edits to `client.ts`: a declaration it does not name
joins `default.types` (`api/types/platform.ts`) or `default.values`
(`api/platform.ts`), a name `client.ts` lost is left out, and a module left
with nothing is not written, each with a note. It refuses, writing nothing,
what it cannot move whole, each refusal the spec's or the source's to
settle: a module over 400 lines or a barrel over 60 (the F1 row's bounds),
a module that exists, statements with side effects that would not move
together to one module the barrel loads (the one move `tsmovecheck`
certifies), a split after which loading the barrel runs side effects in
another order than loading `client.ts` did (`tsmovecheck`'s "effects
reordered"), a runtime import cycle among the modules, one statement's
names placed apart, a module-scope `let` or `var` placed apart from a
statement that assigns it (a module cannot assign a binding it imports,
TS2632), an import that only a local of the same name would use (tsdeclhash
binds by name, and lint fails an unused import), a statement that declares
nothing with no runtime declaration before it, two statements on one line,
`export default` on a declaration or an expression, `export =`,
`import x = ...`, and `declare global` or `declare module '...'`.

Before writing it checks the result as the Refactor guard's class A check
will: `tsdeclhash --no-module` identical and `tsmovecheck`'s pure move,
with evaluation order, over the whole of `src/`, the barrel's surface
(names and what each is bound to) unchanged, every declaration in the
module the plan names, and no type exported in a value list. A failure
there is a fault of the tool, reported apart from a refusal. After writing
it type-checks the root's `tsconfig.json` project and restores every file
on an error (`--no-typecheck` skips that). On its own output it finds
nothing to move and says so. It exits 0 on success, 1 on a refusal or a
failed check, 2 on a usage, spec or read error.

F1's pull request is the generated class A commit, which the Refactor guard
proves with `tsdeclhash` and `tsmovecheck`; a spec change it needs to
regenerate on a newer `master` is a class T commit before it, and the K12
lint rule the F1 row adds is F1's own class T commit, not generated.
`tsdeclmove.mjs` and its tests are guard code (`GUARD_CODE` row S14f); the
spec is not.

Its tests (`cd frontend && node --test scripts/tsdeclmove.test.mjs`) split
`testdata/tsdeclmove/fixture`, a small client in `client.ts`'s shape,
against the goldens under `testdata/tsdeclmove/want`
(`cd frontend && UPDATE_GOLDEN=1 node --test scripts/tsdeclmove.test.mjs`
regenerates them when the tool changes on purpose; only the value `1`
does), type-check the result with no unused import, prove it with
`tsdeclhash` and `tsmovecheck`, compare each declaration byte for byte, and
cover the command line, drift, each refusal, each spec error, a failed type
check restoring the tree, and the self-check refusing each kind of damage
to a rendered move. F1's spec is proved twice. On
`testdata/tsdeclmove/d11dee8`, a copy of `d11dee8`'s `client.ts` and the
five modules it imports (compared with git's copy wherever `d11dee8` is
reachable; CI's one-commit checkout is not), the move type-checks, is a
pure move, keeps the surface S12 snapshots, and keeps the row's bounds and
its `api/http.ts`. On a copy of the repository, the working-tree test
generates F1 and runs what F1's pull request faces: the Refactor guard's
`tsdeclhash` and `tsmovecheck` commands on the commit, `npx tsc --noEmit`,
`npm run lint`, `npx vitest run` with S12's snapshots unchanged byte for
byte, and `npm run build` with the same CSS bytes as before (S12b's check,
ahead of S12b), about 90 seconds. It skips once F1 has landed (`client.ts`
declares nothing) and on a refusal, which it names: a feature pull request
is never failed for one (§8.4), and F1's author settles it in
`specs/F1.json` when regenerating (R4). A gate that fails on the generated
tree still fails the test.

## scripts/refactor/classify_commits.py

```
python3 scripts/refactor/classify_commits.py [-n N] [--first-parent] [--json] [--files] [REV...]
```

Classifies commits by the layers they touch (migration/schema, repository,
domain, handler, route registration, main wiring, frontend client, types,
views/components, CSS, tests, docs, release notes, and the rest), with
files per commit and the hub-touch rates over the five hub files and their
successor `internal/api/routes.go`. It measures the plan's success metrics
(§10) before and after: G1 is the share of code commits (non-test Go, or
TS/CSS under `frontend/src`) touching one or more hubs, and two or more.
On a full clone, `classify_commits.py d11dee8` reproduces the plan's
baseline: 152 of 285 code commits (53%), and 87 (31%). It refuses a range
that reaches a shallow clone's boundary, whose commits git shows as adding
every file (`git fetch --unshallow` first), and `-n` counts every commit,
so "the next 60 code commits" is given as a range.

## scripts/refactor/refactor_guard.py

```
python3 scripts/refactor/refactor_guard.py [--labels TEXT] [--label NAME]... [--merge REV] [--base REV --head REV]
```

The checks of the *Refactor guard* job (S14b,
`.github/workflows/refactor-guard.yml`; CONTRIBUTING.md, "Refactor PRs"),
run on GitHub's merge commit (`HEAD^1` the base, `HEAD^2` the pull
request's head) or on `--base`/`--head`. On every pull request a modified or
deleted golden needs a release note or the `behavior-change` label, and an
added inline snapshot fails; on a `refactor` or `refactor:*` pull request it
adds the frozen and protected paths, the guard-code rule, the ratchet,
lint-allowlist and ceiling rules, and the per-commit class checks read from
the `Refactor-Class:` trailer. Class A runs `declhash` above and, for
TypeScript, `tsdeclhash` and `tsmovecheck` below; class R re-runs the
`Refactor-Script:` in a scratch worktree of the commit's parent. The golden
list, the frozen and protected paths and the guard-code list sit at the top
of the script, each entry naming the plan step that owns it; a later step
adds its entries there in a class T commit. The job, and `make check`, run
the base's copy of the script, so those entries take effect once that pull
request merges (`X2B_CALL_SHAPE_CHANGES` is read from the pull request). The
job's next step, not the script, fails a refactor whose `ratchets.json` can
be tightened.

## make check and make check-fast

`make check` runs CI's pull-request gates locally, in CI's order: the
backend job (gofmt, vet, test, the refactor tools' Python tests, the Postgres
vector assertion against whichever server `OPENV_TEST_DATABASE_URL` names,
which also requires the S3 schema and purge goldens to have run there, with
no subtest skipped, and the same for the S4 boot harness in `cmd/server`,
whose every golden needs a boot that passed, and for the S5 API tour beside
it, whose every golden needs its area's test to have passed, as do
`TestTourCoverage`, `TestTourGoldensAreClaimed`, `TestTourStream`,
`TestTourAccountOptions`, `TestTourMailCatcher`, `TestTourStandIns`,
`TestTourWorker`, `TestTourMatrix` and `TestTourExistenceHiding`),
the release-notes job (against the merge base with `BASE_REF`,
`origin/master`) and the frontend job (tsc, lint, vitest, the Node tests of
`frontend/scripts`, build). The tests of every tool here are part of CI's
gates: the Go ones in the backend job's `go test`, `classify_commits_test.py`
and `refactor_guard_test.py` in its *Refactor tool tests (Python)* step (the
Refactor guard job runs the latter again before using the script), and the
Node ones in the frontend job's *Refactor tool tests (Node)* step. `make
check` also runs the Refactor guard over the commits since the merge base,
with the labels given in `LABELS`. `make check-fast` is the
under-a-minute loop: gofmt, vet, `go test -short` on the packages changed
since the merge base with `BASE_REF` and the packages that import them,
`go test ./internal/archtest`, the S6 source scans in `internal/api`
(`-run '^(TestSSE|TestEventPayload)'`, which read every package whether or
not `internal/api` imports it), and tsc.
